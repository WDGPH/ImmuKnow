# Native workflow and run evidence

The Rust pipeline processes one cohort in a linear sequence: read and preserve source rows, prepare normalized facts and explicit assignments, compile notices with embedded Typst, capture and validate render evidence, optionally encrypt separate copies, assemble bundles, and write the run record and report. Typst templates control prose and presentation. The upstream system assesses immunization status.

Every readable source row receives a stable row key such as `row-000001` in source order. Entries retain the original source values, prepared notice and assignment, observed `checks`, and policy-derived `effective_checks`. Row-level failures are recorded while independent rows continue; a setup or input rejection retains available source rows and unattempted output statuses. The [input guide](../user_guide/getting_started.md) describes the public input contract.

Each run uses a unique output directory staged with an `.incomplete` suffix. Completed work is published under its final name. `run.json` is the authoritative record, and `report.html` is an escaped, readable view. Entries identify the original, optional encrypted copy, findings, route and bundle page range. Output paths use stable row keys, so source identifiers do not become filenames. Run outputs may contain client information and must be kept private.

The executable embeds the shared configuration, schemas and Typst library. `immuknow resources --output DIR` exports them with a hash manifest; authored projects supply templates separately. During compilation the project uses its shared library and local dependencies. Ambient Typst packages and downloads are not supported. Render evidence is checked against its schema, source notice and page bounds; missing or invalid evidence is a failed check but a readable original remains available.

Warnings and failures remain distinct. Warnings are eligible for delivery by default, subject to the effective validation policy. A readable original with failed checks belongs in a separately named review bundle; an unreadable or uncreated original has no bundle membership. Withheld rows have no membership until released. Each included original belongs to one bundle in an attempt, with a CSV listing row identity, page span and findings. Grouping and fixed page count settings are described in [configuration](../user_guide/configuration.md); fixed length never pads a notice.

Encryption produces a separate AES-256 revision 6 PDF and verifies protection and password access before publication. It preserves the original and does not persist the derived password. An encryption failure is recorded separately from the original.

`immuknow rebundle` modifies a saved run without recompiling notices or repeating encryption. It acquires the operating-system `.run.lock` before reading the saved record and holds it through writes. Each attempt stages a new unique bundle directory before publication, so earlier bundles and originals remain available. Delivery uses the saved facts and findings; it does not perform repeated visual or page-by-page comparisons. See [PDF review](../user_guide/pdf_validation.md) for the operator commands.
